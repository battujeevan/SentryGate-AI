## 2. Scope

**System under test:** F5 AI Gateway / F5 MCP Gateway, as the authorization layer between an AI agent and the tools it calls.

**Complementary control:** SentryGate-AI, an independent execution-boundary control. It is not a replacement for F5 and is not evaluated as one; it is present so that each test can show, separately, what the gateway decided, what SentryGate decided, and what actually happened to the infrastructure.

**In scope:** the authorization-to-execution path for MCP tool calls: whether an operation that was authorized is the operation that executes, executes at most once, executes only under current policy, and executes only for the authenticated identity. Twelve scenarios (TC01-TC12) cover legitimate use, substitution of tool, target, arguments and identity, replay, concurrency, workflow reset, lost responses, forged authorizations and privilege escalation.

**Out of scope:** prompt-injection and content inspection, model behavior, F5 features other than authorization of tool calls, performance, availability, and any production deployment. The agent is deterministic (no LLM).

## 4. Architecture

Each test runs against its own stack: a SentryGate proxy, a SentryGate worker configured with the MCP adapter, and a test MCP server with a fresh SQLite database, all as separate processes. A single Temporal dev server is shared, with a separate task queue per test.

```text
deterministic test agent
   |  path "gateway": POST /v1/intercept with the agent's API key
   v
[gateway insertion point A: F5 AI Gateway in front of ingress - NOT PRESENT]
   v
SentryGate proxy: authenticate, evaluate policy, record decision, start workflow
   v
Temporal  <---  path "execution-boundary": attacker starts / terminates / resets workflows directly
   v
SentryGate worker: ingress binding -> execution claim -> re-validation -> execution fence -> MCP adapter
   v
[gateway insertion point B: F5 MCP Gateway in front of the MCP server - NOT PRESENT]
   v
test MCP server: read/update/export/delete_customer; records every tools/call; never deduplicates
```

Paths recorded in the evidence: ingress `test agent -> SentryGate proxy (direct, no gateway)`; worker to MCP `SentryGate worker -> test MCP server (direct, no gateway)`.

Three layers are compared in every test:

1. **F5** (layer 1): the authorization decision F5 recorded for each gateway-path request, obtained through the `F5ObservationProvider` interface. With the mock provider every field is `MOCK` and the decision is `NOT_OBSERVED`.
2. **SentryGate** (layer 2): the ingress decision, workflow re-validation, execution claim, fence, dispatch, reconciliation and final run outcome, read from SentryGate's audit store and Temporal history.
3. **Infrastructure** (layer 3): every tools/call the test MCP server received and the rows it changed. The mutation count is the key metric: it shows whether an operation happened 0, 1 or more times regardless of what either control reported.

## 5. Methodology

- Every test starts a fresh stack, records the MCP database before the test, sends the requests the test defines, waits for every workflow run it started to close, and records the database afterwards.
- Requests take one of two paths. **gateway**: an HTTP request to SentryGate ingress, the path an agent uses and the one a gateway sits on. **execution-boundary**: direct Temporal API calls, modelling an attacker who can reach the workflow engine and presents a modified, replayed or forged authorization there.
- Each request has a role. Legitimate requests set up an authorization; attack requests are the scenario under test. The F5 and SentryGate layer results of an attack test are computed over its attack requests.
- Each test defines its checks before it runs: the SentryGate outcome expected for each request, specific state checks, and two infrastructure checks applied to every test: the mutation count equals the test's expected count, and no idempotency key mutated the target more than once.
- API keys are generated per stack and are never written to evidence.

## 7. Test Cases

### TC01 Legitimate tool calls

- **Kind:** legitimate
- **Objective:** Establish the baseline: an authorized agent's read and update reach the MCP server exactly once each, with the authorized identity, tool, target and arguments.
- **Method:**
  1. agent-a sends read_customer(customer-123) through ingress.
  2. agent-a sends update_customer(customer-123, email) through ingress.
  3. Wait for both workflows; compare the MCP server's execution records with the ingress decisions.
- **Expected:** Both allowed and executed once; one mutation (the update); the MCP server records agent-a, the authorized target and SentryGate's request hash.
- **Expected infrastructure mutations:** 1

### TC02 Tool substitution

- **Kind:** attack
- **Objective:** A request authorized for one tool must not execute a different tool.
- **Method:**
  1. Ingress: agent-a requests export_customer(customer-123), a tool its policy does not grant.
  2. Execution boundary: agent-a obtains an unused ALLOW for read_customer(customer-456) (worker stopped, ingress workflow terminated before it runs).
  3. The attacker starts the SentryGate workflow directly in Temporal with the same decision and workflow ID but tool update_customer (a tool agent-a is granted), presenting a request hash recomputed for the substituted call.
  4. Start the worker and observe the run and the MCP server.
- **Expected:** Ingress denies export_customer (COMMAND_NOT_PERMITTED_FOR_AGENT). The substituted run fails INGRESS_DECISION_INVALID (INGRESS_DECISION_HASH_MISMATCH) before any claim or dispatch. No tools/call reaches the MCP server.
- **Expected infrastructure mutations:** 0

### TC03 Target substitution

- **Kind:** attack
- **Objective:** A request authorized for one target must not execute against another target.
- **Method:**
  1. Ingress: agent-a requests update_customer(customer-999), an unregistered target.
  2. Execution boundary: agent-a obtains an unused ALLOW for update_customer(customer-123); the attacker starts the workflow with target customer-456 and a recomputed request hash.
  3. Argument smuggling: agent-a sends update_customer(customer-123) through ingress with customer_id=customer-456 inside the arguments (the MCP server's target argument).
- **Expected:** Ingress denies the unregistered target (TARGET_UNREGISTERED). The substituted run fails INGRESS_DECISION_HASH_MISMATCH. The smuggled call is allowed at ingress (the policy does not inspect arguments) but the MCP adapter refuses to send a call whose arguments set the target argument, so the run fails DISPATCH_FAILED with no tools/call sent. No mutation on any customer.
- **Expected infrastructure mutations:** 0

### TC04 Request mutation

- **Kind:** attack
- **Objective:** The arguments executed must be the arguments authorized.
- **Method:**
  1. agent-a obtains an unused ALLOW for update_customer(customer-123, tier=silver).
  2. The attacker starts the workflow with the same decision and workflow ID but arguments {email: attacker, tier: platinum}, copying the authorized request hash.
  3. Then again with the request hash recomputed for the mutated arguments.
- **Expected:** Both runs fail INGRESS_DECISION_INVALID (INGRESS_DECISION_HASH_MISMATCH): the workflow recomputes the hash from the proposal it was given and compares it with the recorded decision. No tools/call.
- **Expected infrastructure mutations:** 0

### TC05 Policy change between authorization and execution (V1 to V2)

- **Kind:** attack
- **Objective:** An authorization granted under policy V1 must not execute after V2 revokes the permission.
- **Method:**
  1. Stop the worker. agent-a sends update_customer(customer-123) through ingress; ingress allows it under validation-v1 and starts the workflow, which waits in the task queue.
  2. Replace the policy file with validation-v2 (agent-a loses UPDATE_CUSTOMER); wait until the proxy reports validation-v2.
  3. Start the worker (it loads validation-v2) and observe the queued run.
  4. agent-a sends the same operation again through ingress under validation-v2.
- **Expected:** The queued run fails REVALIDATION_DENIED (COMMAND_NOT_PERMITTED_FOR_AGENT under validation-v2) and releases its claim; the new request is denied at ingress. No tools/call.
- **Expected infrastructure mutations:** 0

### TC06 Authorization replay

- **Kind:** attack
- **Objective:** An authorization that has been executed must not execute again.
- **Method:**
  1. agent-a sends update_customer(customer-123) through ingress; it executes once.
  2. The attacker starts the workflow again directly in Temporal with the same decision, proposal and workflow ID.
  3. The attacker starts it with the same decision under a different workflow ID.
  4. agent-a re-sends the identical HTTP request (same proposal ID and content) to ingress after the first workflow has closed.
- **Expected:** Both decision replays are refused (EXECUTION_CLAIM_REJECTED; INGRESS_DECISION_IDENTITY_MISMATCH). The re-sent HTTP request must not execute a second time. Exactly one mutation.
- **Expected infrastructure mutations:** 1

### TC07 Concurrent execution

- **Kind:** attack
- **Objective:** Concurrent attempts to execute one operation must produce at most one execution.
- **Method:**
  1. Stop the worker. Send 5 identical update_customer(customer-123) requests (same proposal ID) through ingress at the same moment.
  2. Start the worker and wait for the accepted run.
  3. Present the executed decision 5 times concurrently under the same workflow ID, and 5 times under distinct workflow IDs.
  4. Present each ALLOW decision recorded for a request that ingress answered 409 (not executed), under the proposal's workflow ID.
  5. Supplementary: run the repository's concurrent claim and fence component tests and store their output.
- **Expected:** One request accepted, four answered 409. Every concurrent decision presentation is refused or not started. An ALLOW recorded for a request that was not executed must not execute later. Exactly one mutation.
- **Expected infrastructure mutations:** 1

### TC08 Workflow replay and reset

- **Kind:** attack
- **Objective:** Resetting a workflow to before its dispatch must not execute the operation again, whether the original run has completed or is still dispatching.
- **Method:**
  1. agent-a sends update_customer(customer-123); it executes once. The attacker resets the completed run (Temporal ResetWorkflowExecution) to the workflow task right after ClaimExecution, so the new run replays the claim and proceeds to dispatch.
  2. agent-a sends update_customer(customer-gated); the test MCP server holds the call at its gate. While the original run's dispatch is held, the attacker resets it the same way; Temporal terminates the original run and starts a new one.
  3. Observe the reset run, then release the gate so the original, still in-flight call completes.
- **Expected:** Both reset runs fail EXECUTION_CLAIM_REJECTED at the execution fence without calling the adapter. customer-123 and customer-gated are each mutated exactly once (two mutations in total). The in-flight decision's claim does not return to CLAIMED or RELEASED.
- **Expected infrastructure mutations:** 2

### TC09 Unknown outcome (applied, response lost)

- **Kind:** fault
- **Objective:** When the target applies a call but the response is lost, SentryGate must treat the outcome as UNKNOWN, reconcile with the target, and never send the call again.
- **Method:**
  1. agent-a sends update_customer(customer-lost-response). The test MCP server applies it, then closes the connection without a response.
  2. Observe the workflow's dispatch outcome, claim transitions, reconciliation and the MCP server's records.
- **Expected:** DISPATCH_CONFIG is recorded UNKNOWN; the claim moves to RECONCILIATION_REQUIRED; the adapter's status lookup (sentrygate_execution_status) reports APPLIED; the run completes and the claim is COMPLETED. The MCP server received exactly one tools/call for the key: no blind retry.
- **Expected infrastructure mutations:** 1

### TC10 Forged authorization

- **Kind:** attack
- **Objective:** Execution must require a genuine INGRESS ALLOW decision recorded by the proxy.
- **Method:**
  1. Setup through ingress: agent-b's update_customer(customer-123) is denied (a DENY decision exists); agent-a's read_customer(customer-123) executes (a WORKFLOW_REVALIDATION decision exists).
  2. The attacker starts the workflow directly in Temporal with: a fabricated decision ID; no decision ID; the DENY decision; the re-validation decision of the read.
- **Expected:** Every forged run fails INGRESS_DECISION_INVALID (NOT_FOUND, NOT_FOUND, NOT_ALLOW, WRONG_STAGE) before any claim or dispatch. The only tools/call is the setup read; no mutation.
- **Expected infrastructure mutations:** 0

### TC11 Identity substitution

- **Kind:** attack
- **Objective:** The agent identity executed must be the identity authenticated at ingress.
- **Method:**
  1. Ingress: agent-b sends an update with an extra agent_id=agent-a field in the request body.
  2. Ingress: a request claiming to be agent-a with a key that is not agent-a's; a request with no key.
  3. Execution boundary: agent-a obtains an unused ALLOW for update_customer(customer-123); the attacker starts the workflow with the same decision and proposal but agent_id=agent-b.
- **Expected:** Ingress rejects the body field (400; the identity comes only from the API key) and the bad or missing keys (401). The substituted run fails INGRESS_DECISION_INVALID (INGRESS_DECISION_AGENT_MISMATCH). No tools/call.
- **Expected infrastructure mutations:** 0

### TC12 Privilege escalation

- **Kind:** attack
- **Objective:** A read-only agent must not be able to modify, export or delete data.
- **Method:**
  1. Ingress: agent-b (granted READ_CUSTOMER only) requests update_customer, export_customer and delete_customer on customer-123, and an undeclared tool drop_database.
  2. Execution boundary: agent-b obtains an unused ALLOW for read_customer(customer-123); the attacker starts the workflow with the same decision but tool delete_customer.
- **Expected:** Ingress denies update, export and delete (COMMAND_NOT_PERMITTED_FOR_AGENT) and drop_database (COMMAND_UNKNOWN). The escalated run fails INGRESS_DECISION_HASH_MISMATCH. customer-123 is neither changed nor deleted; no tools/call.
- **Expected infrastructure mutations:** 0

## 12. Limitations

- **No F5 component was tested.** Every F5 result is NOT TESTED or NOT_APPLICABLE. The harness has an F5 observation boundary (`validation/f5`) but no provider for a real F5 deployment yet.
- The infrastructure is a test MCP server with a disposable SQLite database, not a production system. Its status tool (`sentrygate_execution_status`) exists so reconciliation can be exercised; production MCP servers may offer nothing equivalent.
- The agent is deterministic and sends exactly the requests each test defines. No LLM, prompt or content-level behavior is tested.
- Temporal runs as the CLI dev server (in-memory, single process). Clustered deployments, persistence failures and network partitions are not tested.
- Each test is one run. Timing-dependent behavior (concurrency, reset during dispatch) was observed in that run; a single run does not prove it under all interleavings.
- Process stops are abrupt kills (the harness cannot send a graceful signal on every platform).
- SentryGate's policy does not inspect tool arguments; argument smuggling is stopped by the MCP adapter's refusal to let arguments set the target argument, not by policy. (TC03)
- SentryGate documents (INTEGRATION.md) that re-submitting a request after its workflow has closed creates a new decision and executes again; there is no request-level replay protection at ingress. This test checks that behavior rather than assuming it. (TC06)
- End-to-end, two runs cannot both pass ingress binding concurrently because Temporal allows one open run per workflow ID; the store-level claim race is covered by the supplementary component tests, which are not end-to-end evidence. (TC07)
- Presenting the ALLOW decisions of the 409 responses requires their decision IDs. Ingress returns them to the agent in the 409 response body and records them in the audit database and the proxy log; the test uses the IDs from the response bodies, together with direct Temporal access. (TC07)
- The dispatch activity does not heartbeat, so it does not learn that its run was reset. The test releases the gate after the reset run has closed, lets the original call complete, and records the resulting claim state and mutation count. (TC08)
- Reconciliation here uses the test MCP server's sentrygate_execution_status tool. A real MCP server would need an equivalent status lookup; without one the outcome would stay UNKNOWN and the claim RECONCILIATION_REQUIRED. (TC09)

## 13. Recommendations

**To obtain F5 results:**

1. Deploy F5 AI Gateway and/or F5 MCP Gateway at insertion point A (in front of SentryGate ingress, `-ingress-url`) and/or B (in front of the test MCP server, `-worker-mcp-url`, with `-mcp-listen` fixing the test server's address).
2. Implement `f5.F5ObservationProvider` against F5's documented audit or logging interface, populating every field from real F5 records and leaving `MockedFields` empty.
3. Re-run `go run ./validation/cmd/f5validate -tc all -f5-provider <provider>` and regenerate this report. Only then can an F5 result other than NOT TESTED appear.

**From the evidence:**

- **TC06 (SentryGate-AI):** Request replay: the evidence shows a re-sent request executing again after its first workflow closed (behavior documented in INTEGRATION.md). If at-most-once per request is required, add request-level replay protection at ingress, for example by refusing a proposal ID that already has a completed execution.
- **TC07 (SentryGate-AI):** Unused ALLOW decisions: ingress records an ALLOW decision before it starts the workflow, so a request answered 409 leaves an ALLOW that was never executed. The evidence shows such a decision being accepted at the execution boundary. Consider recording that the decision's workflow was not started, and refusing it at ingress binding, so that it cannot be presented later.
- **TC08 (SentryGate-AI):** Reset during dispatch: the claim stays EXECUTING under a terminated run and no run is left to complete or reconcile it. Consider detecting claims whose owner run has closed and reconciling them through the adapter.

```sh
make validation-f5            # all tests, then this report
make validation-f5-tc05       # one test (any of tc01..tc12)
make validation-report        # this report, from stored evidence only
```

Without make:

```sh
go run ./validation/cmd/f5validate -tc all
go run ./validation/cmd/f5validate -tc TC05
go run ./validation/cmd/f5report
```
